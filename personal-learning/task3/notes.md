# 第 3 章初学者笔记：记住什么，怎样找回来

## 1. “记住”至少有三层

第一层是把刚说过的事实找回来；第二层是从多次会话中拼出同一件事的全貌；第三层是尚未被追问时，也能发现与当前请求有关的旧信息。我现在会先看题目属于哪一层，再讨论记忆方案的好坏。作者保存的四模式评估里，增强笔记总体得分最高，但 Advanced JSON Cards 在第三层达到 95%、第二层只有 60%。一种格式没有包办所有任务。

记忆写入和记忆取回也是两件事。把整段对话长期塞进提示词会越来越贵；只留下短卡片则可能丢掉时间、来源和冲突。更稳妥的做法，是保留可追溯的原始记录，同时用可更新的索引和摘要帮助定位。

## 2. 检索不是一个按钮

BM25 先按词项建倒排索引，利用词频、文档频率和长度算分。它很适合产品名、编号和明确术语。本机 3-5 的精确词 Recall@5 是 100%，纯同义词查询却是 0%：词没出现，算法再认真也找不到。

稠密向量把语义相近的文本放到相近位置，可以补上部分同义改写。ANNOY 和 HNSW 是在向量已经生成后，帮我们更快找近邻的索引。它们解决的是查找速度和更新方式，不会替嵌入模型理解文本。作者历史对照中两者召回都为 1.0，但 ANNOY 增量更新要重建，HNSW 可追加。

混合检索先把词法与语义结果合并，再按需要重排。RRF 主要融合名次，加权融合依赖分数尺度。重排要多花模型时间，且这章保存的 3-6 小数据里，它没有比稠密检索提高 MRR。我会把“阶段更多”与“结果更好”分开看。

## 3. 找到片段，还要找到关系

RAPTOR 用摘要树把细节逐层汇总，适合先问概念、再追具体段落；GraphRAG 把实体和关系连起来，适合跨片段追问“谁依赖谁”。本机的 3-7 只是预置图和树的示意，真正建索引时仍要检查 LLM 是否把原文关系抽错。

Agentic RAG 让模型决定是否继续搜、改写什么查询、何时停止。本机 3-8 离线题中，多轮检索的证据召回确实高于一次检索，但子查询是事先写好的。那说明“多查几次有机会补证据”，还不能说明模型一定会自己想到正确的下一问。真实轨迹还应检查引用、延迟和错误行动。

## 4. 对话碎片需要上下文

“好的，就订这个吧”离开前一轮对话几乎没有检索价值。上下文感知检索先给片段补上简短背景，再把两者一起索引。作者 3-10 的历史活动里，BM25 的 Recall@1 从 60% 到 80%；本机 3-11 的八问离线教学集从 62.5% 到 75%。前缀有用，但也会增加索引成本；而且我这次没有重新用 LLM 生成前缀。

用户记忆最终可以分两层：少量重要、可更新的卡片常驻；大量原始对话按需检索。作者 3-11 的 60 题中，普通窗口、上下文前缀、双层结构的总体通过率依次为 78.3%、86.7%、95%。这是一份历史对照，仍需看卡片是否准确、旧事实是否过期、检索是否找到了冲突证据。

## 5. 隐私和隐性知识

长期保存之前还要脱敏。本机 3-3 的正则规则保留信息最多，却漏下 9 处；混合策略在这 12 条合成日志里没有残留泄漏，但误删更多信息。脱敏的目标是同时降低泄露和保留排错线索，单个百分比讲不全。

3-12 把许多判例抽成因子，再聚成案件原型，最后只按这些统计结果给建议。我把它理解为“从一堆个案里找可解释的共性”。但作者保存的原始 CAIL 压缩包未随仓库提供，我本机没有重跑；判例建议还必须回到原文、适用条件与不确定性。

## 我会怎样读结果

先确认数据是本机运行、离线预置案例，还是作者历史活动；再看查询、索引、模型和裁判是否同一组；最后同时读召回、排序、延迟、引用和错误。一个漂亮的 Recall@k 只说明证据更可能进了候选集，还没有替最终回答签字。
