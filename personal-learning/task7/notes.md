# 第 7 章｜评估笔记

我这次先拿已有客服轨迹重新算成本。朴素、只用缓存、只做压缩和两者一起用是四组不同的记录，价格按脚本内的假设重算。这不是今天新调用模型的账单，但很适合看钱到底花在哪几轮。以后比较模型，我不能只把单价排一列，还得算重试和重复输入。

## 分数在回答什么问题

Pass@k 看多次尝试里至少有一次成功，连续成功的要求则要看多次都通过。前者适合找能力上限，后者更接近“能不能放心交给它”。我在读 τ²-bench 的任务时，也会同时看初始状态、允许动作、预期终态和验证器，不能只记一个通过率。

Rubric 把“答得怎么样”拆成可以判断的项目，模型裁判仍需要校准。我会看它是否有原始任务、证据和评分理由，也会留意换一种表达格式，判定会不会跟着变。7-7 的历史格式对照文件恢复成 Git 原始字节后，哈希相关测试通过；Windows 自动换行就足以让完整性检查失败。

## 出错要往前找

最后一句答错，不一定是最早出错的地方。AndroidWorld 的失败归因需要顺着动作和观察找第一处偏离，再把那段前缀变成回归任务。只给“失败”标签，下一次仍不知道应该改哪里。人工执行基准、语音盲评和模型行动阈值的历史记录，我读的也是任务与轨迹对应关系。

排行榜还受投票样本、顺序和评分模型影响；Elo 的分数不是脱离数据的能力刻度。嵌入、重排、主模型的组合比较，则要保持同一题集，否则很难判断提升来自哪一层。

## 这次还没有测到的范围

有些清单提到的完整报告没有进入当前 Git 快照，我在逐项表里按缺失处理。7-11 要求的长上下文大样本、限流爬坡和 168 小时可用性活动，也没有在这次短运行里完成。AndroidWorld 全套和 OpenVLA/RoboTwin2 更需要完整模拟器、模型与数据，现有测试通过不代表新的整套 benchmark 已经跑完。

我给结果保留了样本数和运行条件，差几道题的时候尤其不能省略它们。[实验记录](experiment.md)和[逐项进度](progress.md)可以回查到对应文件。
