# Task 1 学习笔记：从 1-1 到 1-4

这份笔记用初学者能复述的话记录“我看到了什么、它为什么重要、怎样检查自己有没有看错”。实验数字与证据见[实验过程](experiment.md)，完成范围见[进度结果](progress.md)。

## 1. Agent 到底由什么组成

`Agent = LLM + 上下文 + 工具` 是我目前最容易记住的简化公式。模型做下一步决策；上下文是它这一步能看到的信息；工具让它获取外部信息或执行动作。环境可能是网页、文件或其他系统，工具只是连接环境的接口。

## 2. 先学会看 ReAct 循环（1-2）

模型读取上下文，决定是否调用工具；工具执行后，结果作为新消息进入上下文，模型再决定下一步。离线搜索示例有两轮“思考 → 行动 → 观察”：第一次结果不够完整，才触发第二次搜索。

我以前容易把 Agent 想成“一次提问、一次回答”。离线轨迹让我看到，每次工具返回都会成为下一轮的新输入。但离线演示的搜索结果是预写的；真正验证联网搜索，还要检查服务端工具调用、状态和来源链接。终端里出现 `web_search` 字样，并不能单独证明搜索已经执行。

## 3. 工具定义与工具结果不是一回事（1-1）

工具定义告诉模型“能做什么”；工具结果告诉模型“刚才执行后发生了什么”。我的两组对照都能调用计算器，但 `no_tool_results` 组看不到返回值。即使本地工具已经算出 4000，模型也不能用这个观察值确认答案。

我把五种上下文模式理解为五个不同的问题：`full` 是基线；`no_history` 测过去几轮消息的作用；`no_reasoning` 测保留先前推理文本是否有帮助；`no_tool_calls` 直接撤掉工具定义；`no_tool_results` 让工具执行后模型看不到观察值。撤掉工具定义以后不能调用工具是由请求结构决定的，不应包装成模型“学会了不用工具”。

补齐五组后，我看到 `no_history` 连续 10 轮重复计算器调用仍未回答；`no_reasoning` 却只用 2 轮正确回答，说明去掉先前推理**不一定**使这种简单任务变差。`no_tool_calls` 输出了看似调用计算器的一串文字，但真实工具调用数是 0。这也提醒我：必须区分文本里“像调用”的内容和 API 记录中的实际工具事件。

## 4. 结果正确不等于过程可靠

在我的算术对照里，两组答案都为 4000；完整组只用 2 轮、1 次工具调用，隐藏工具结果组用了 7 轮、6 次调用。只看最后一个数字，我会错过重复调用和无依据回答的风险。评价 Agent 时，我现在会同时看答案、来源、执行轨迹、耗时与成本。

## 5. 搜索负责取数，代码负责计算（1-3）

首都距离问题需要两种能力：搜索提供坐标，Python 按同一公式比较所有配对。我检查的不是回答中写了“已搜索、已计算”，而是结果 JSON 中真正完成的 `web_search_call` 和 `code_interpreter_call`，以及代码运行日志。十个首都两两配对共有 `10 × 9 ÷ 2 = 45` 对；这次代码得出吉隆坡与新加坡约 315.29 公里。

公里数不是孤立的“标准答案”。坐标可以取市中心、政府所在地或不同数据库的位置，距离会略有变化。遇到时效性或定义不清的任务，还要先说清楚时间、国家集合、数据源与采用的坐标口径。请求“做比特币技术分析”时，如果数据源和指标未指定，就应该先澄清。我的第二个用例确实先询问偏好且没有调用工具；补充数据源与指标后，才继续联网搜索并运行代码。

这次 API 排障给我的另一个启发是：看到 `Bad Request` 不能立刻归因于欠费。先核对地域、业务空间地址、实际发出的请求字段，再用没有工具的最小请求区分接口问题和工具参数问题。密钥只检查是否存在、长度和前缀，不打印明文。

## 6. 工作流多一步，可能帮忙也可能丢信息（1-4）

文生图工作流是固定的“需求 → 改写提示词 → 生图”两步；直接生图是一部到位。比较时，我先列出用户的硬要求，再看改写词有没有保留，最后看图片。耳机海报中，原要求必须出现指定文案，历史改写词却把 `text` 放进负面提示词。这一步已经丢了要求；后面的生图模型再强，也难以在被要求“不要文字”的条件下补回文案。

宽泛的“AGI 后程序员”没有指定构图。改写词加上“人喝咖啡、机器人写代码”，让画面有了明确叙事；直接生图也能构思出类似情景。因此要分别判断**保留约束**和**补充创意**，不能只问哪张“更好看”。这次四张图是同一工具的单次小对照，不能归因为仓库原版的 Kimi 或万相模型性能。

## 7. Harness 与编排

Harness 负责构造上下文、接入工具、管理循环，并加入约束和验证。固定步骤可以用工作流；任务需要根据环境反馈动态选择路径时，再使用更自主的 Agent。复杂度应该由任务和评估结果决定。

## 8. 我现在会用的检查清单

- **输入：**用户真正要求什么，哪些是必须满足的条件？
- **上下文：**Agent 每轮收到哪些消息？有没有删掉历史、工具定义或工具结果？
- **行动：**工具是否实际执行并完成？结果是否返回给模型？
- **证据：**来源链接、代码日志和最终结论能否对应？
- **比较：**两组是否只改变了想研究的因素？模型、数据和次数不同要明确写出。
- **成本：**轮数、工具调用、耗时和 Token 使用是否明显增加？
