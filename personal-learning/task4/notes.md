# 第 4 章初学者笔记：工具是边界，也是选择

## 1. 先分清工具在做什么

感知工具把环境信息带进来，例如读取文件、搜索网页；执行工具会改变状态，例如写文件、运行代码；协作工具把任务交给其他人或 Agent，或者等待批准与回信。看一条工具调用时，我现在会先问：它只是观察，还是已经动了外部世界？这个区分决定了需要多少验证和授权。

MCP 把工具目录、参数和返回值组织成统一接口。模型拿到一个工具名称还不够，参数描述要清楚，失败结果要能解释原因；否则它可能“会调用”，却不知道调用是否达到目的。

## 2. 工具太多，要学会按需找

一次塞进上百个 schema，会占用上下文。我的 4-1 离线演示里，全量注入用了 93,040 token；主动发现用了 7,796。一次性预筛选虽然也省 token，却在八个任务里漏掉四个后续要用的工具。多步任务的下一种需求，未必在第一句查询里就看得出来。

这仍是脚本化模型的机制演示。作者的真实 Qwen3-4B 对照中，两组都完成了三题；主动发现更快，却没有准确率提升。节省上下文与提高正确率应分别量，不能从前者直接推出后者。

## 3. 感知要保留信息，也要控制范围

本机 4-2 的离线流程先 grep，再精读文件，最后查询本地知识库。它让我看到“先定位、再展开”的好处：不用把整份材料一下塞给模型。网络和私有日历没有在离线演示中执行；历史正式活动也因 Google Calendar、Notion 缺授权而未完成所有门禁。能列出工具，不代表已经取得读取私有数据的许可。

## 4. 图片里的数字，未必在文字里

4-3 的柱状图明明写着 Q4 为 180M，PDF 正文却没有四个季度的精确数值。如果只抽取文本，问题的关键证据会消失。原生多模态能直接看图片；先转写为文字依赖提取质量；按需工具分析更灵活，也可能花更多时间。作者四问历史对照里，原生和工具路线各答对四题，文本路线一题未对。样本小，我只把它当作信息保真度的提醒。

## 5. 执行要能拒绝

我用 4-4 CLI 写了一个合法 Python 文件，它通过语法检查；故意写坏的代码被挡住，试图写到工作区外的路径也被挡住。这些失败是有价值的结果。执行工具除了返回“完成”，更要留下验证、错误原因和必要时的审查记录。外部日历、邮件、GitHub 之类的操作，还得分别看权限和幂等性。

## 6. 协作是持续中的状态

子 Agent 有创建、运行、回复、取消；人工审批有待处理、批准、拒绝、超时。超时之后的迟到回复不能悄悄让旧操作重新生效。我在 Windows 上复测 4-5 时，发现原脚本用 `select()` 等待匿名管道会失败；改成可超时轮询后，相关测试通过。这里让我体会到：协作工具最重要的输出，有时不是一条消息，而是清楚的状态边界。

## 我的检查顺序

1. 先分工具类别：读、写，还是交给人或其他 Agent。
2. 核对输入 schema、权限、作用范围和返回值。
3. 对执行动作看验证与回滚可能，对协作动作看超时与重复回复。
4. 最后读成本与成功率。离线 mock、作者历史运行和本机真实调用要分开。
