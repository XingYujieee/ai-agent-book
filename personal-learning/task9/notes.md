# 第 9 章｜持续进化笔记

之前我连续指出笔记写得太像 AI，这件事正好让我能具体理解本章的用户反馈：加几次“第一人称”并没有把问题解决，句子节奏和整篇结构都得重新看。把一次纠正存下来容易，换一篇仍能用得自然，才值得继续测。

## 反馈要落在哪一层

事实过期适合更新资料，表达和流程偏好可以写进 Skill，明确的重试或权限逻辑更适合改代码，较稳定的语言习惯才可能需要参数训练。我不想遇到一个错误就往系统提示里添一句，旧规则越来越多，冲突也会一起留下来。

轨迹验证的离线例子里，“说已经退款”却没有相应动作，被事实和承诺一致性项目判了失败。这里的质量判断用了启发式规则，我没有把它当成真实模型裁判。客服经验提炼的历史活动则要看新规则有没有改善迁移集，而不只是把同一道题答对。

## 本机小模型的澄清对照

9-4 原项目还缺完整实现，我补了一组本地决策试验：六个固定请求，分别用普通提示、追加一句用户反馈、带作用范围的 Skill，模型都是 qwen3:0.6b。三组分别答对 3/6、2/6、4/6，没有 API 错误。

结果没有好到可以直接发布。Skill 组能在 Spec 已确认后选择执行，却仍对明确的小改动和只读请求多问一次。把反馈原样追加，甚至少答对了一题。这只是十八次本机决策调用，没有真实用户交互，也没有验证整套开发任务的交付质量，但已经能看出“多写一条规则”会带来什么副作用。

## 一条经验什么时候能复用

浏览器工作流演示先存候选，再 reset 后回放，通过才进入可复用状态；页面变化后，原来的状态谓词不成立，流程会失效并回退。它用的是离线页面状态，不是这次新跑了一遍浏览器网站。

安全门禁的 quick 运行接受了确定性候选，拒绝了放行一切的反例。本机测试还发现 Windows 下双重解码后的 /etc 路径没有按预期识别，这次把两种路径语法都纳入检查后复测通过。改进提案是否采用，仍由外部检查决定。

## 更新也包括淘汰

9-9 的参考 Agent 对照里，只追加经验的策略能学到旧规则，规则变化后却没恢复；带版本替换的策略可以在收到变更信号后修订。这里的参考 Agent 是确定性程序，真实模型结果另外保存在作者的历史活动中。自我修改、Hermes 和长期演化的完整正式活动，我这次没有重新执行。
